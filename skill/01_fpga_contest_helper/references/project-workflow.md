# 项目启动、需求与阶段出口

## 确认赛道和资料

先读资料索引，查当前年度的总通知、所选杯赛/题目原文、平台要求和提交说明。逐项标出来源页/章节、版本/日期和仍待核实项。没有原文时可以草拟需求，不虚构比赛规定。报名日期、队伍资格、指定平台、IP/开源/AI 使用条件和提交材料需在当前来源确认，不能从同名旧届、另一个赛道或厂商示例推定。

选题未定时按用户已有板卡、器材、团队能力、时间和最难验证环节比较少量方案，给可做的最小功能与风险，不自动替用户选厂商。采购或具体平台推荐先查当前一手资料。

## 从需求到设计

为每项需求建立 ID：原文来源→输入/输出→量化阈值→模块→仿真用例→板级试次→报告证据。阈值缺失时记录待确认；自行选择的工程目标注明“内部目标”。

先确定最低可交付系统、主要创新点及测量方法，再扩展。架构说明数据流、时钟/复位域、吞吐、端到端延迟、缓存、位宽/精度、资源预算和故障处理。解释哪些功能在 FPGA 并行逻辑中，哪些在软核/SoC/主机中，以及是否符合题目限制。

模块接口先明确 valid/ready、背压、空满、数据保持、帧界与复位中断事务的语义。资源、延迟与精度的预算是估算；综合和实测后更新，不伪造 LUT/FF/BRAM/DSP 数量。

## 阶段出口（项目内工程建议）

| 阶段 | 进入下一阶段所需的最小证据 |
| --- | --- |
| 需求与平台 | 原文定位、可测验收条件、板卡已知/未知清单、最高风险验证计划 |
| 架构与最小系统 | 顶层接口、时钟/复位图、最小链路测试；无板卡时先做平台无关模型 |
| 模块开发 | 自检仿真及边界场景、必要静态检查、明确参数限制 |
| 集成 | 接口与 CDC 审查、系统级回归、真实综合/实现报告 |
| 板级验证 | 实际下载件身份、输入/供电/复位条件、测量结果与失败试次 |
| 发布 | 同一版本的工程、约束、报告、下载件、重复验收与恢复步骤一致 |

可按任务迭代，不把所有阶段变成阻塞普通文档工作的审批清单。首次板级时钟/LED 测试也应先核对实际硬件并做必要仿真/实现。

临近截止时保留可回退版本，优先完成全链路验收、报告和演示恢复。时间比例与重复次数由项目风险决定，不复制固定电赛四天节奏。
