# 技能包的提炼过程

**配套文档**：`skill/README.md`、9 个 `skill/*/SKILL.md`、`report/07_llm_collaboration.md`

---

## 1. 为什么不是“先写模板再填内容”

早期也试过“列一个技能清单，再往里填步骤”。结果是：写出来的东西像教科书，换一个队伍、换一块板就不能用，因为里面没有“什么时候会错”的判断。

后来改成从失败反推：

```
现象 → 可区分假设 → 最小实验 → 根因 → 修法 → 回归判据 → 边界 → 技能
```

只有走完这一圈，才允许写成技能。原因是：

- **没有现象**，技能就不知道“什么时候该用”；
- **没有假设**，技能就退化成“照做”；
- **没有回归判据**，技能就无法验证“修好了没有”；
- **没有边界**，技能会被误用到不该用的地方。

## 2. 九条提炼路径

| 技能 | 触发失败/观察 | 根因 | 回归判据 | 边界 |

## 3. 三个“从失败到技能”的完整例子

### 3.1 例一：峰值 DSP 的回绕（`rtl_dsp_pipeline`）

**现象**：同一份 `frame.csv`，xsim 与 Python 参考都是 `0x8001C105CD`，板上读到 `0x8005900BE6`；`idx` 偏 33，`amp` 偏 15–50%。

**假设与排除**：

1. 算术错？xsim 逐位对 → 排除；
2. NCO 相位错？全相位扫描只落在 idx 448–452 → 排除；
3. 取窗错？三种取窗差 1–2 样本 → 排除；
4. 解码错？40 位切片后字段一致 → 排除；
5. 锁存时机错？一次脉冲后 1.5 s 内字被改写三次，帧号一直是 1 → **命中**。

**根因**：`active` 只在 `capture_start` 置位，从不清零；`sid` 16 位回绕（65,536 样本 = 13.1 ms）后每次回到 539 就重新锁存。

**修法**：窗口走完 `active <= 0`；`peak_strobe` 每拍默认清零；tb 加“帧后 66,000 样本”回归。

**为什么写成技能**：这个 bug 的核心不是“某一行代码”，而是“仿真的覆盖不够”。技能里因此有一条硬性要求：**tb 必须喂超过计数器位宽**。任何做定点 DSP 的人都会遇到同类问题。

**边界**：逐位一致只证明“板和 PC 算得一样”，不证明回波是真的；所以技能里单独写了这一条。

### 3.2 例二：24 点环少 14.34°（`scanning_3d_reconstruction`）

**现象**：圆柱模型看起来像螺旋，层与层之间接缝错位。

**根因**：24 方位需要 23 次移动，每次 171 counts（15°），23×171=3933，而一圈是 4096；每层少 163 counts = 14.34°。下一层又从 `rot 0` 开始，累积成螺旋。

**修法**：每层第一个点补 `rot 163`，3933+163=4096；建模时 `--az-per-ring 0`。

**为什么写成技能**：这不是“代码 bug”，是“计划生成器的算术”。任何用步进电机做环扫的人都会遇到；技能里因此给了可 grep 的判据（`rot 171` 出现 23×layers 次）。

**边界**：只适用于“每步固定 counts”的环扫；如果使用编码器闭环或连续旋转，逻辑不同。

### 3.3 例三：`-nolog` 压掉 `-log`（`fpga_capture_bringup`）

**现象**：交接单要求带回 `build_m3.log`，但文件不存在；构建本身成功。

**根因**：命令同时有 `-nolog` 和 `-log`，`-nolog` 把日志压掉。

**修法**：去掉 `-nolog`；排查时看 `synth_1/runme.log`、`impl_1/runme.log`。

**为什么写成技能**：这类“工具参数互斥”不会报错，只会让证据消失；技能里因此要求“构建结束必须检查日志存在且非空”，并把“日志不存在”列为失败。

**边界**：不同 Vivado 版本的参数行为可能不同；技能里写了版本（2025.1），换版本要复核。

## 4. 怎么验证一个技能“有效”

每个技能设有三种验证方式，不要求都做，但至少做一种：

### 4.1 回放验证

把技能里的步骤在一份**已知结果**的数据上重跑，看是否得到同样的数字/判据。例如：

- `rtl_dsp_pipeline`：用 `sim/vectors/samples.hex` 重跑 tb，应得到 `0x80011B07E0`、`STROBES=1`；
- `scanning_3d_reconstruction`：用 `data/reference/bench/` 重跑 `run_bench.py`，应得到 MAE 0.189 mm；
- `scanning_3d_reconstruction`：重跑 `run_anomaly.py`，应得到 8/8、0 误报。

### 4.2 负例验证

故意制造一个已知错误，看技能是否能提前拦住。例如：

- 把 24 点环的最后一点删掉，计划检查应报“每层少 163 counts”；
- 把 `active` 的停机删掉，tb 的 66,000 样本回归应报 `STROBES>1`；
- 把引脚 diff 正则换回旧版，脚本应因“解析不到”而 error，而不是打印“no differences”。

负例验证比正例更能说明技能“有判断力”。

### 4.3 换环境验证

把技能里的板卡相关部分替换掉，看是否还能用：

- 换时钟/引脚：只改约束，步骤不变；
- 换 ADC 位宽/采样率：改 `FRAME_CYCLES`、分频、窗口样本号；
- 换 IMU：改寄存器初始化，融合与字格式不变；
- 换 PYNQ 板：`pynq_overlay_io` 只依赖 overlay/MMIO/DMA。

本项目做了前三种的“纸面推演”，没有换板实测；因此技能里把“替换点”单独列出，避免下一个队伍以为“照抄就行”。

## 5. 为什么是 9 个，不是 20 个

最初按模块拆成 9 个“专用小块”：采集、DSP、帧握手、姿态、建模、异常、构建、证据、PYNQ。这种拆法有两个问题：换一个题目是否还能用；工作区里已有的通用技能为什么没有纳入。

这一版做了三件事：

1. **合并同一条链上的技能**：
   - 采集 + 构建 → `fpga_capture_bringup`（都要“先证明数字链路，再证明构建可复现”）；
   - DSP + 帧握手 → `rtl_dsp_pipeline`（都要“同一帧、同一字、完整读走”）；
   - 建模 + 异常 → `scanning_3d_reconstruction`（异常是建模网格上的残差，不是另一条链）；
   - 证据 + 提交审查 → `evidence_review`。
2. **补通用技能**：
   - `fpga_contest_helper`：工作区已有的 FPGA 竞赛流程，含 5 个 references；
   - `pynq_overlay_io`：面向 PYNQ 的通用 overlay/AXI/DMA；
   - `mechanical_design_to_print`：从 `3Dprinter/design_output` 提炼出的机械/打印/装配链；
   - `procurement_search`：工作区已有的国内采购/比价技能。
3. **明确不收的**：
   - `team-handoff`：依赖 SCAN 团队网页和成员绑定，换队伍不可用；
   - `Vivado 安装/license`、`Python 虚拟环境`：太环境相关，不是工程判断；
   - `如何写 README`：没有本项目特有的失败，写出来是空话；
   - `如何做 PCB`：本项目没有做 PCB，不能编。

最终的 9 个是“5 个方法 + 4 个通用”：既不碎，也不是为了凑数。

## 6. 技能与“可复用性”评分

赛题要求“一支陌生队伍拿到该目录，能否直接用在自己的题目上”。按这一标准逐项自检：

| 检查 | 结果 |
|---|---|
| 是否绑定本队探头/板卡型号 | 核心步骤不绑定；型号放在“输入/替换点” |
| 是否绑定超声 | 01/02/03/05/06/07/08/09 可迁移；04 是领域方法，但几何/质量门/残差思路可迁移 |
| 是否有可复制命令 | 每个技能至少 3 条 |
| 是否有失败判据 | 每个技能至少 3 条 |
| 是否写清“不承诺什么” | 每个技能都有“边界” |
| 是否有验证数字 | 01–04、08 有实测/仿真/CAD 数字；07 明确标注未执行部分；06/09 是工作区既有通用技能 |
| 是否能被 agent 直接读 | YAML front matter + 分节，适合作为系统提示 |

## 7. 技能包的维护

- 每次新踩坑，先写“现象—根因—判据”，再决定是否合并进现有技能；
- 技能里的数字必须来自 `data/` 或 `build/reports/`，不能凭记忆；
- 换板/换工具后，先跑“回放验证”，再改技能；
- 失效条件比步骤更重要：步骤会过时，失效条件不会。

---

## 8. 结论

技能包不是“项目文档的缩写”，而是“判断的集合”。它记录的是从“板上对不上”走到“逐位一致”，从“螺旋模型”走到“闭合环”，从“日志消失”走到“日志必须存在”。

只读一个文件时可读 `skill/README.md` 的第 2 节；只读一个技能时可读 `02_evidence_review`，它决定其他八个技能是否会被误用。
