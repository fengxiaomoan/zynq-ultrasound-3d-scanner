# 大模型协作记录

**项目**：基于 AMD Zynq-7020 的实时超声三维扫描与形态异常检测系统  
**记录范围**：2026-09 至 2026-10-27，RTL、仿真、构建、PS 固件、上板、文档全流程  
**协作工具**：本地 AI 编程智能体（DeepSeek Harness 会话），可读写工作区、执行 PowerShell/Python、调用 Vivado/Vitis 命令行  
**说明**：本文不是逐字聊天记录，而是按会话交接单、代码注释、构建日志和证据文件还原的关键节点。原始日志在 `data/`、`sim/results/`、`board/logs/`；每条结论都能回到具体文件。

---

## 1. 为什么用大模型，以及不让它做什么

这个项目的难点不是“写一个模块”，而是**在真实硬件上把一条跨 PL/PS/PC 的链路调到可复现**。它有三个特点：

1. 反馈慢：一次综合实现约 10 分钟，一次上板加载可能失败，一次扫描几十分钟；
2. 状态多：位流、ELF、XSA、引脚、约束、VIO 探针、ILA 探针、固件版本，任何一处不一致都会让现象不可解释；
3. 容易“看起来对”：仿真绿、时序过、页面能开，都不等于声学链路成立。

因此项目把大模型定位为**执行型协作者**，而不是“答案生成器”：

- **让它做**：读现有代码/日志、提出可验证的假设、写最小复现、改一处、跑构建/仿真、整理证据、写交接单；
- **不做的事**：代替人判断“实测通过”、选择硬件参数、在没跑的情况下写“已验证”、把仿真数字写成实测、擅自改冻结工程；
- **硬约束**：每次只改一类文件；改动前说明涉及文件、目的、风险；没有日志/哈希/JSON 的结论一律标“未验证”。

这条边界不是形式主义。项目里至少有三次，模型给出的“合理推断”被后续实测推翻；也正是这些推翻，最后沉淀成了技能包。

## 2. 智能体工作流设计

### 2.1 角色分工

项目按“阶段 + 单一职责”拆成多个会话，每个会话只对一类产物负责：

| 会话 | 职责 | 主要产物 | 退出判据 |
|---|---|---|---|
| P0 契约 | 定寄存器、帧格式、接口、判据 | `acq_axi_regs.v` 头注释、`M2B_README` §4 | 双方对“一帧是什么”无歧义 |
| P1 RTL/DSP | 峰值/质心 DSP、仿真、上板逐位 | `peak_dsp.sv`、`tb_peak_dsp.sv`、`dsp_hw_compare.json` | 同帧逐位一致 |
| P2 构建/上板 | 位流、XSA、引脚、加载、时序 | `build_ps_m3_pkg.tcl`、`load_m3_pkg.tcl`、报告 | `M3_BUILD_DONE` + WNS/WHS ≥ 0 |
| P3 PS/网页 | 帧读取、环形缓冲、C 算法、HTTP | `acq.c`、`alg.c`、`model.c`、`net.c` | C 与 Python 逐字节一致 + 页面冒烟 |
| P4 姿态 | MPU6050、融合、AXI 窗口、页面 | `pose_fusion.sv`、`/api/pose` | 130 向量逐位 + 板上 716.6 Hz |
| P5 证据/文档 | 证据分级、报告、技能包 | 本仓库 `report/`、`skill/` | 每条结论有文件 |

### 2.2 每轮的固定动作

每个会话开始时，先做四件事，再动代码：

1. 读 `README`/交接单/当前状态，确认“现在到哪一步”；
2. 列本次要改的文件和**不改**的文件（红线）；
3. 选一个能在 10 分钟内跑完的最小验证（仿真/单测/构建/一次上板）；
4. 把“预期现象”和“失败判据”先写下来，再执行。

结束时，交接单必须包含：请求、状态、已完成、决策、文件、真实验证、阻塞、下一动作、踩坑。没有“已验证”的证据，就写“未执行”。

### 2.3 证据门

每个阶段都有“门”，不过门不进入下一阶段：

| 门 | 判据 | 不过怎么办 |
|---|---|---|
| G1 语法/仿真 | `xvlog`/`xelab` 通过，tb 打印 PASS | 先修编译，不综合 |
| G2 构建 | `M3_BUILD_DONE`，WNS/WHS ≥ 0，DRC 0 error | 不改约束“凑过”，先查路径 |
| G3 引脚 | 只多 `scl T10`/`sda T11`，无 LOST/换脚 | 重新解析 `io.rpt`，不靠“日志没报错” |
| G4 上板 | `ping` 通、`/api/status ok`、`frames` 增长 | 断电重来，不在坏状态继续扫 |
| G5 算法 | C `points.csv` 与 Python 逐字节相等 | 查 `t_eff`、列名、浮点格式 |
| G6 证据 | 每个数字有文件、有 provenance | 退回补日志，不写“约” |

## 3. 五类提示词模式

### 3.1 “先读后写”模式

> 先不要改代码。读 `fpga/rtl/peak_dsp.sv`、`fpga/tb/tb_peak_dsp.sv`、`tools/dsp_ref.py`，用一段话说明：40 位字的每一位由哪个always块驱动、`capture_start` 如何复位、峰值窗结束后 `active` 应该是什么。然后再提出修改方案，一次只改一个文件。

**作用**：防止模型在没读懂时序的情况下“顺手重构”。这个模式在峰值 DSP 的回绕 bug 上救了两次——第一次模型想改比较器，读完发现根因是 `active` 没有清零。

### 3.2 “证据优先”模式

> 不要引用旧文档里的数字。只允许使用以下文件里的数字：`live_run/_m2b_ps_rate.log`、`_m2b_rate.log`、`dsp_hw_compare.json`。每个数字后面写文件名和行号；找不到就写“无证据”，不要估算。

**作用**：项目里出现过“90.9 fps”被误写成“100 fps”、“2.48–2.80 ms”被写成“2 ms 以内”。证据优先模式把这类漂移压住了。

### 3.3 “失败复现”模式

> 板上读到 `0x8005900BE6`，参考算 `0x8001C105CD`，同一份 CSV 在 xsim 里与参考一致。请列出至少 5 个可区分假设，并为每个假设设计一个最小实验（不超过 10 分钟），按“能排除最多可能性”排序。先不要改 RTL。

**作用**：把“猜”变成“排除”。峰值 DSP 的定位过程就是按这个模式走的：排除算术、NCO 相位、取窗、解码，最后用“一次脉冲后连读 4 次”抓到了字被反复改写。

### 3.4 “红队审查”模式

> 你现在是评审。请逐条审查这份报告里的数字：哪些是实测、哪些是仿真、哪些是外推？如果有“把仿真写成实测”“把帧率写成精度”“把加载失败解释成功能问题”的表述，逐条指出并给出更准确的写法。

**作用**：这是最后一道防线。`F1_工作总结` 里的“九条红线”、`M2B_WORK_SUMMARY` 里的“不能引用”清单，都是红队审查的产物。

### 3.5 “交接单”模式

> 写一份给下一个会话的交接：只写三件事——现在能跑什么、哪些数字能引用（带文件）、哪些不能引用（带原因）。不要写过程感慨，不要写“建议进一步优化”这种空话。最后列三条下一动作，每条要有判据。

**作用**：项目跨了多个会话，交接单是唯一不丢状态的东西。好的交接单能让下一个会话在 10 分钟内接上，而不是重新读一遍 3 GB 日志。

## 4. 八个代表性协作案例

### 案例 1：峰值 DSP 的 40 位字在板上“对不上”

**背景**：RTL 仿真与 Python 参考逐位一致，但上板读到的 `idx` 总比同帧 CSV 的参考大几十到一百多，`amp` 也偏大 15–50%。

**提示词（摘要）**：

> 同一份 `frame.csv`：xsim 输出 `0x8001C105CD`，参考也是，板上却是 `0x8005900BE6`。请按“能排除最多假设”的顺序设计实验，不要先改 RTL。特别注意：VIO 读的是锁存字，ILA 抓的是波形，两者时间关系是什么？

**模型回答（摘要）**：先排除算术（xsim 已对）、NCO 相位（全相位扫描复现不出）、取窗（三种取窗只差 1–2 样本）、解码（40 位切片正确）；然后建议做“一次脉冲后每 0.5 s 读一次字”的实验。

**实验结果**：一次脉冲后 1.5 s 内字被改写三次（372/2534 → 395/2607 → 422/2715），而 `frame_count` 一直是 1。根因是 `active` 只在 `capture_start` 置位、从不清零；`sid` 16 位回绕（65,536 样本 = 13.1 ms）后每次回到 539 就重新锁存，把字改写成 ADC 自由运行时任意 560 点的结果。

**修复**：窗口走完 `active <= 0`；`peak_strobe` 改成每拍默认清零。仿真加回归：帧后继续喂 66,000 样本，要求 `STROBES=1 WORD_STABLE=1`。

**结果**：四轮独立采集 `MATCH: True`，`idx_delta=0`、`amp_delta=0`；VIO 2.48–2.80 ms vs ILA 477–555 ms。

**沉淀**：`rtl_dsp_pipeline` 技能；核心教训是“仿真只喂 560 点，永远碰不到回绕，必须喂超过 65,536 点”。

### 案例 2：姿态字整体右移 8 位

**背景**：F1 首次上板，`/api/pose` 能返回，但 roll/pitch/yaw 全部错位，像被“右移了 8 位”。

**提示词（摘要）**：

> 姿态字按 `{magic,seq,flags,tick,roll,pitch,yaw,pad,err}` 拼接，PS 读到的 yaw 像被右移 8 位。请检查每个字段的位宽和拼接顺序，特别是有没有 8 位字段被零扩展到 16 位。

**模型回答（摘要）**：列出 128 位字段表，指出 `err_cnt` 只有 8 位，拼接时被零扩展成 16 位，导致后面所有字段右移 8 位；`flags` 是 7 位拼进 8 位寄存器，位序也错。

**修复**：`err_cnt` 扩到 16 位；`flags` 显式补 0；加一个 130 向量的 PC 参考模型，逐位比对。

**沉淀**：`sensor_fusion_ui` 技能；同时记录了另外三个“差 1 count”的坑：`-0` 被当负数、CORDIC 输入取了带符号 `ax` 而不是 `|ax|`、静止时 pitch 差 1 count。

### 案例 3：网口“时通时不通”，GIC 中断不确定

**背景**：MAC `RXCNT` 在涨、`ISR` 挂着 `0x82`，但 lwIP 收不到包；`XScuGic_CfgInitialize()` 偶尔能好两次，之后又失效。

**提示词（摘要）**：

> `ping` 不通，但 MAC 的 RXCNT 在涨、ISR 一直挂着、lwIP 的 recv_q 为空。请区分“MAC 没收到”“中断没进 CPU”“中断进了但没投递到 lwIP”三种情况，给出可观测的判据，不要直接改 GIC 配置。

**模型回答（摘要）**：建议在 `netif->input` 装计数器、读 `GICC_*` 回读、检查 `ISRENABLER1`/`ITARGETSR54`。并提醒 `GICC_*` 是 banked 寄存器，JTAG 读不了，只能让固件把回读写到 GPIO。

**实验结果**：分发器使能、目标 CPU0、MAC IMR 都正确，但 ISR 从不执行；`XScuGic_CfgInitialize()` 的行为非确定。

**修复**：不再依赖 GIC——关掉 IRQ54，主循环直接调用 `XEmacPs_IntrHandler()`，网络路径完全不经过 GIC。之后 60 次 ping / 约 45 s，0 失败。

**沉淀**：`rtl_dsp_pipeline` 技能里的“中断不确定时，先做轮询兜底，再查根因”；以及“banked 寄存器不能 JTAG 读”的调试经验。

### 案例 4：层索引爆炸，`/state` 返回空模型

**背景**：三层扫描后 `/state` 是空模型，`alg_compute()` 返回 -1。

**提示词（摘要）**：

> 扫描三层，`layers` 应该是 `[2,0,-2]`，但固件里层索引涨到几百。请检查 `ingest()` 里层索引的更新条件，注意一次 2 mm 抬升是 4096 counts，不是 8 counts。

**模型回答（摘要）**：旧逻辑“变化超过 8 counts 就 ++”在 4096 counts 的抬升过程中会触发几百次；建议改成按绝对位置量化 `ki = lround((lift0 - lift)/4096)`，并丢掉偏离层网格 >0.25 层的抬升中途帧。

**修复**：按绝对位置量化后，三层 `72/71`、六层 `141/131`，网格 144/192、288/480。

**沉淀**：`scanning_3d_reconstruction` 技能；教训是“不要把‘变化’当‘层’，层是绝对量化的”。

---

### 案例 5：构建日志被 `-nolog` 压掉，引脚 diff 门“静默通过”

**背景**：交接单要求带回 `build_m3.log`，但命令同时有 `-nolog` 和 `-log`，日志根本不生成；引脚 diff 脚本解析 2025.1 的 `io.rpt` 格式失败，空表被当成“没有差异”。

**提示词（摘要）**：

> 构建命令是 `vivado -mode batch -nojournal -nolog -notrace -source build_ps_m3.tcl -log build_m3.log`。请确认 `-nolog` 和 `-log` 是否互斥；另外检查引脚 diff 脚本的正则是否能匹配 `| T10 | scl | ...` 这种格式。不要为了让门通过而改判据。

**模型回答（摘要）**：`-nolog` 会压掉 `-log`，日志不会生成；`io.rpt` 是管道表格式，旧正则 `^\s*(\S+)\s+(\S+)\s+([A-Z]+\d+)` 匹配不到，导致 diff 恒为空。建议去掉 `-nolog`，并把正则改成 `^\|\s*([A-Z]+\d+)\s*\|\s*(\S+)\s*\|`；解析不到就 `error`，不静默通过。

**结果**：手工重算引脚：m2 168、m3 170，ADDED 只有 `scl T10`/`sda T11`，无 LOST、无换脚。

**沉淀**：`fpga_capture_bringup` 技能；核心原则是“门禁脚本解析不到时必须报错，不能把空表当通过”。

---

### 案例 6：C 算法与 Python“看起来一样”，但浮点格式不一致

**背景**：PS 的 C 算法与 Python 参考在数值上接近，但 `points.csv` 不能逐字节相等。

**提示词（摘要）**：

> 不要用“误差小于 1e-3”作为通过标准。请让 C 和 Python 输出同样的列、同样的精度、同样的 `repr` 格式，逐字节比较；如果不一致，先定位到第一处不同的字节，再解释原因。

**模型回答（摘要）**：指出 C 的 `printf("%.6f")` 与 Python 的 `repr()` 在尾数和负零上不同；建议统一用固定小数位、统一 `t_eff` 的传递路径、把 `peak_max` 列的历史怪癖（写的是 `peak_med`）保留并注明。

**结果**：4 个真实 run（928/919/1203/408 帧）的 `points.csv` 逐字节相等；`/state` 每格 `t/r/n` 差 <1e-3。

**沉淀**：`rtl_dsp_pipeline` 技能里的“等价性要定义到字节，不是定义到感觉”。

### 案例 7：姿态 716.6 Hz，不是 1 kHz

**背景**：目标是 1 kHz，实测 716.6 Hz。

**提示词（摘要）**：

> 采样率实测 716.6 Hz，目标是 1 kHz。请从 I2C 读周期、DLPF、融合节拍三个层面拆解时间预算，指出哪一段可以压缩，哪一段不能；不要直接改分频凑数。

**模型回答（摘要）**：3 ms DLPF + 0.4 ms I2C + 融合 51 拍 ≈ 1.4 ms，主要瓶颈是“读完再等 1 ms”的旧排程；建议改成从突发读起点按绝对 tick 排程，把等待重叠掉。

**结果**：修法进源码，但**未在板上复测**；报告里仍写 716.6 Hz，不写 1 kHz。

**沉淀**：`sensor_fusion_ui` 技能；以及“红线：不写 1 kHz，除非复测到 1 kHz”。

### 案例 8：红队审查，删掉三句“漂亮话”

**背景**：报告初稿写了“实现 1 kHz 姿态”“整机 190× 加速”“检测 8 mm 缺陷”。

**提示词（摘要）**：

> 逐条审查这三句话：① 1 kHz 姿态；② 整机 190×；③ 检出 8 mm 缺陷。每句找出支持文件；找不到就删掉或改成有证据的写法。

**模型回答（摘要）**：

- “1 kHz”实测 716.6 Hz，且页面 20 Hz——改成“716.6 Hz 采样、20 Hz 页面”；
- “整机 190×”是单帧回读 171–202×，整机扫描受电机限制约 3.3 s→2.3 s——改成“单帧回读加速，整机约 30%”；
- “8 mm 缺陷”是仿真凸起，实物 10 mm 凸起在旧窗口下无签名——改成“真实凸起待定量”。

**沉淀**：`evidence_review` 技能；这是全项目最重要的一条纪律。

## 6. 模型出错的地方与防错措施

### 6.1 典型错误

1. **把“合理”当“已验证”**：模型曾根据代码推断“I2C 400 kHz 下 1 kHz 采样没问题”，实测只有 716.6 Hz。防法：任何时序结论必须有一次板上计数。
2. **改生成物而不是源**：曾建议直接改 `page_html.h`，但它是 `tools/live_model_page.html` 生成的。防法：先问“这个文件是生成物吗”，改源再重新生成。
3. **为了过门而改判据**：引脚 diff 解析不到时，模型曾建议“把 error 改成 warning”。防法：门禁脚本的红线写死，改判据必须单独评审。
4. **把仿真绿当功能完成**：峰值 DSP 仿真一直绿，但上板错。防法：三级验证链，仿真只是第①级。
5. **文档数字漂移**：同一指标在不同文档里出现 90.9/91/100 三个版本。防法：单一事实源（`data/real/` 的日志），文档只引用，不复制。

### 6.2 防错机制

- **单一事实源**：帧率只认 `_m2b_ps_rate.log`，回读只认 `dsp_hw_compare.json`，资源只认 `build/reports/`；
- **provenance 字段**：每个 JSON/CSV 头写 `real-measurement`/`synthetic`/`RTL-sim`；
- **红线清单**：每个交接单末尾列“不许写的说法”；
- **红队审查**：提交前让模型扮演评审，逐条找“无证据表述”；
- **可复现命令**：每条结论附一条能重跑的命令，跑不动就降级为“未验证”。

## 7. 可复用的提示词模板

### 7.1 接手项目

```
先读 README、HANDOFF、当前状态、证据索引。用 10 行以内回答：
1) 现在能跑什么；2) 哪些数字能引用（文件名）；3) 哪些不能引用（原因）；
4) 下一动作及判据。不要改任何文件。
```

### 7.2 定位硬件不一致

```
现象：板端读到 X，参考算 Y，仿真 Z。请列 5 个可区分假设，
为每个设计一个 ≤10 分钟的实验，按“排除最多”排序。
先不要改 RTL；每个实验写清预期现象和失败判据。
```

### 7.3 写构建/上板脚本

```
写一个 PowerShell/Tcl 脚本，要求：
- 任何输入文件不存在时立即退出，不碰板子；
- 每一步打印可 grep 的标记（BUILD_OK / LOAD_OK / PING_OK）；
- 失败时保留现场，不自动重试超过 N 次；
- 不修改冻结工程，不覆盖旧位流。
```

### 7.4 写文档

```
把这段工作写成给人看的报告：先结论，再证据，再边界。
每个数字后面标 provenance（real/sim/static）和文件。
禁止使用“显著提升”“大幅优化”这类无法核对的词。
如果某个结论没有证据，写成“未验证”，不要省略。
```

### 7.5 提交前红队

```
你是评审。逐条检查：
- 有没有把仿真写成实测？
- 有没有把帧率写成精度？
- 有没有把加载失败解释成功能问题？
- 有没有“约/左右/接近”但没有误差范围的数字？
逐条给出修改建议。
```

## 8. 结论

大模型在这个项目里最大的贡献，不是“写了多少行代码”，而是**把每一次失败变成了下一次可执行的实验**，并且把这些实验固化成技能包和门禁。它也会犯错——推断过度、数字漂移、想改生成物——所以必须用证据链、红线和红队审查把它约束住。

如果要用一句话总结这套协作方式：**让模型负责“下一步怎么做”，让人负责“这一步算不算数”。**
